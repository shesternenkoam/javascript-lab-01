# Lab 1: Event Loop та Ігровий Цикл

Цей проєкт — реалізація ігрового циклу для браузерної гри (керування космічним кораблем) з використанням патерну **"Fix Your Timestep"**. 

Проєкт демонструє роботу з `requestAnimationFrame`, відділення логіки фізики від рендеру, обробку вводу через замикання та інтерполяцію кадрів для забезпечення плавності на будь-яких моніторах.

## Експерименти та аналіз Event Loop

В рамках лабораторної роботи було проведено три експерименти зі свідомим "ланням" архітектури для аналізу поведінки Event Loop.

### Експеримент 1: Блокуючий цикл у кадрі
**Що було зроблено:** У функцію `update` (фізика) було додано жорсткий синхронний цикл `while`, який штучно затримує виконання на 100 мс щокадру.
**Результат:** Гра повністю "зависає", FPS падає до 1-5 кадрів на секунду, керування стає нечутливим.
**Пояснення:** 
Браузер має лише один головний потік для виконання завдань (Call Stack). Якщо ми даємо йому важкий шматок коду, він не може робити нічого іншого, поки не закінчить. Через це браузер просто не має часу дійти до фази малювання (Paint) або перевірити чергу завдань (Task Queue), де лежать наші натискання клавіатури.

### Експеримент 2: setInterval замість requestAnimationFrame
**Що було зроблено:** Виклик `requestAnimationFrame(frame)` замінено на `setInterval(() => frame(performance.now()), 1000/60)`.
**Результат:** Гра продовжує працювати, але рух корабля стає "смиканим" і менш плавним, з'являються візуальні розриви, незважаючи на стабільний крок фізики.
**Пояснення:** 
`requestAnimationFrame` працює в ідеальній гармонії з монітором — він викликає код рівно перед тим, як екран збирається оновити картинку. А `setInterval` — це звичайне фонове завдання (Macrotask). Він кидає команду на виконання в чергу і "не знає", коли саме екран буде малювати. Через цю розсинхронізацію ми бачимо мікрозатримки та ривки.

### Експеримент 3: Змінний крок (Variable Timestep) замість фіксованого
**Що було зроблено:** Було видалено акумулятор (цикл `while`), і у функцію `update(dt)` почав передаватися реальний, змінний час між кадрами (`frameTime`) замість жорстких 16.6 мс.
**Результат:** При стабільних 60 FPS усе виглядає нормально. Проте, якщо згорнути вкладку браузера на кілька секунд, а потім розгорнути, корабель за один кадр "телепортується" на величезну відстань.
**Пояснення:** 
Коли вкладка неактивна, браузер заради економії ресурсів сильно сповільнює виклики `rAF`. Коли ми повертаємося, `frameTime` стає гігантським. Якщо ми множимо швидкість корабля на такий великий `dt` за один раз, ми отримуємо величезний стрибок координат. Фіксований крок з акумулятором вирішує цю проблему: він "наздоганяє" пропущений час рівними, безпечними кроками, гарантуючи, що симуляція завжди детермінована і об'єкти не пролітають крізь стіни за один лагаючий кадр.
